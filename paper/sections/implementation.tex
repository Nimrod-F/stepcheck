\section{Implementation}
\label{sec:impl}

The framework of Section~\ref{sec:approach} is realised directly as \texttt{stepcheck}, a single
dependency-light Rust command-line tool of \textbf{6{,}728} source lines (excluding a 900-line test
suite) that follows the pipeline of
Figure~\ref{fig:arch-detail}, covering eight analysis passes, four front ends, the \asl{}
emitter, and the self-validation tooling.

\emph{soundness tier}, and required premise. This is the reader's lookup table: it separates
must-fix errors from warning-level adoption checks, and proven native facts from declared or advisory
premises.

Two small extension interfaces realise the architecture: a \texttt{Frontend} lowers an input
format to the IR, and a \texttt{Pass} analyses that IR and emits diagnostics. Behind them sit the
typed DSL, raw \asl{}, CNCF Serverless Workflow~\cite{cncfServerlessWorkflow}, and a
\textbf{CloudFormation / SAM / CDK} front end; all share the same IR and pass implementations
(Section~\ref{sec:eval:cncf}). The raw-\asl{} front end lowers
generic JSON with a stack-growing deserializer, parsing all 193 corpus workflows and the
nested-\texttt{Map} stress cases without error.

\paragraph{Running on the deployment artifact.}
A serverless team rarely commits a standalone \asl{} file: the state machine lives inside a
CloudFormation or SAM template (a \texttt{DefinitionString} with \texttt{!Sub}/\texttt{!GetAtt}
intrinsics) or is generated by CDK. The CloudFormation front end reads such a template---or a
\texttt{cdk synth} output template---directly: it finds every
\texttt{AWS::StepFunctions::StateMachine}, resolves the intrinsics (keeping the AWS pseudo-parameters
exact so service-integration ARNs survive, mapping resource references to placeholder ARNs), follows
local \texttt{DefinitionUri} references, and lowers each machine to the same IR.
\texttt{stepcheck check template.yaml} and
\texttt{stepcheck check cdk.out/Stack.template.json} therefore work with no manual extraction, which
makes the build-time gate (Section~\ref{sec:eval:industrial}) a drop-in check on the deployed
artifact rather than on a separately prepared definition.

\paragraph{Running the verifier.}
\tool{} is a single self-contained binary, packaged for \texttt{crates.io} and \texttt{npm}
(packaging details in the technical report). A developer runs \texttt{stepcheck check workflow.json}
on an existing definition; \texttt{--infer} lights up the semantic checks from name and resource
conventions, \texttt{--annot sidecar.toml} supplies declared schemas/protocol/effects
(Section~\ref{sec:approach:annot}), and \texttt{--result-shapes} enables closed output records for
declared task results and common AWS service envelopes. Findings render for a terminal or, with
\texttt{--json}, as a stable machine record (code, severity, state, message, remediation).

By default the exit status is \texttt{0} (clean), \texttt{1} (any \emph{error}), or \texttt{2}
(parse failure). The \emph{recommended CI policy} fails a build on errors---the sound native and
declared-tier findings---while leaving \emph{inferred warnings} non-blocking. This lets a repository
adopt \tool{} without triaging heuristic findings up front. \texttt{--deny-warnings} tightens the
gate once a repository wants warnings to block. The artifact ships a runnable GitHub Actions gate
(\texttt{.github/workflows/gate.yml}) that enforces this policy on every push/PR and self-tests, via
an injected defect, that the gate actually blocks it.

Nothing else is deployed: the check reads the ingested \asl{} and never re-emits it, so raw-\asl{}
verification is entirely independent of the emitter.

The remaining components validate the verifier itself. First, a data-flow certificate checker
recomputes the widened invariant and checks finite proof obligations: the start invariant, every
normal/catch transfer as a post-fixpoint condition, and every emitted \code{SC1101} as a definite
absence query in that invariant. This discharges loops by induction over the fixpoint rather than by
bounded unrolling (Section~\ref{sec:eval:dataflow}). Second, a code-disjoint execution oracle
re-interprets a workflow concretely along bounded loop-unrolled paths and cross-checks the same
conclusion; this is an empirical differential check in the sense of test oracles and translation
validation~\cite{oracleproblem,difftestanalyzers,translationvalidation}, not the proof itself.
A mutation command injects one defect of a chosen class and re-emits deployable \asl{} for the study
in Section~\ref{sec:eval}.

\paragraph{Implementation limitations.}
Distributed \texttt{Map} item contexts are modelled coarsely. The \asl{} emitter---used as the
DSL's code generator and in evaluation harnesses---now carries uninterpreted \asl{} fields through
the IR. Round-tripping 193 workflows preserves $100\%$ of states and all measured I/O-processing
fields (including JSONPath, JSONata, and Map item-selection fields), gives exact \asl{}-object
equality for $99.5\%$ of workflows, and leaves \texttt{emit} idempotent on all 193
(Section~\ref{sec:eval:roundtrip}). This is an \asl{} round-trip guarantee; deployment wrappers such
as CloudFormation metadata remain outside the emitter.
