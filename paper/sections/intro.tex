\section{Introduction}
\label{sec:intro}

Cloud-native applications increasingly decompose business logic into independently
deployable functions that are coordinated by managed \emph{workflow orchestration}
services. Among these, AWS Step Functions has become one of the most widely
adopted platforms in industry~\cite{wen2021empirical,kulkarni2025characterizing}.
A Step Functions workflow is a state machine written in the \emph{Amazon States
Language} (\asl), a JSON configuration format that describes task invocations,
branching, parallelism, retries, and error handling, and that executes on top of
AWS Lambda and dozens of service integrations~\cite{awsStepFunctions}.

While orchestration platforms simplify \emph{running} distributed workflows, they
provide little support for \emph{reasoning about workflow correctness before
deployment}. An \asl{} state machine is an untyped artifact: the platform validates
its JSON schema and the existence of transitions, but not whether the data produced
by one task matches what the next consumes, whether tasks are invoked in a valid
business order, whether an automatically retried task is safe to repeat, or whether
a long-running transaction can roll back the effects it has already committed. As a
consequence, four recurring classes of defect surface only at run time (detailed in
Section~\ref{sec:bg:defects}): \emph{contract mismatches} (a task reads a field its
predecessor never produces); \emph{protocol/typestate violations} (a task runs out of
business order---shipping before payment); \emph{unsafe retries} (a retry re-invokes a
non-idempotent operation, duplicating its effect~\cite{mohammad2025resilient}); and
\emph{missing compensation} (a persistent operation cannot be rolled back when a later
step fails---an incomplete Saga~\cite{garciaMolina1987sagas}).

A central obstacle to checking these properties is that \asl{} \emph{omits the very
information the checks require}. \asl{} has no notion of a task's input or output
type, no business-state labels, no idempotency annotation, and no concept of
``compensation'' beyond a generic \texttt{Catch}. Existing language-level
approaches sidestep this by introducing a new programming model with a proprietary
runtime~\cite{burckhardt2021durable,zhang2020beldi,temporal}; but the millions of
workflows already written in \asl{} cannot benefit, and re-platforming is rarely an
option.

\paragraph{Approach.}
We present \tool, a static verifier that brings four complementary checks to
serverless workflows \emph{before deployment} while remaining fully compatible with
AWS Step Functions. \tool{} is organised around two ideas. First, a \emph{two-layer}
analysis model: a set of \emph{native} checks operate soundly on raw \asl{} with no
extra input (structural well-formedness and \asl{}-semantic data-binding checks),
while a set of \emph{semantic} checks (typestate, retry safety, compensation) draw
on a lightweight \emph{annotation} layer. Second, because most existing workflows
carry no annotations, the missing semantics are \emph{inferred} from task names and
resource bindings by a documented, configurable heuristic, giving a zero-effort
default analysis that developers can override or refine. Verified workflows are
compiled back to executable \asl, so \tool{} introduces no runtime component and no
lock-in. A typed builder frontend additionally lets greenfield workflows be authored
with full static guarantees and the same compilation target.

\paragraph{Contributions.}
\begin{itemize}
  \item A practical model and four static analyses ---contract/data-flow, typestate,
        retry safety, compensation completeness--- plus a native structural pass (five
        in all), framed operationally rather than through heavy formalism
        (Sections~\ref{sec:approach}--\ref{sec:analyses}).
  \item A two-layer design that verifies \emph{existing} \asl{} workflows by pairing
        sound native checks with an annotation layer whose defaults are inferred
        from naming/resource conventions (Section~\ref{sec:approach}).
  \item \tool, an open, modular Rust implementation (2.6k LOC) with pluggable frontends
        (raw \asl, a typed DSL, the CNCF Serverless Workflow DSL), a diagnostics engine,
        an \asl{} emitter, and a mutation-based error-injection tool
        (Section~\ref{sec:impl}).
  \item An evaluation on \textbf{193 real} workflows: in-the-wild findings, a 429-mutant
        study (100\% recall) contrasted with the \texttt{statelint} validator,
        inference accuracy and warning precision against an agreement-checked gold set,
        sub-millisecond cost, and a real AWS round-trip (Section~\ref{sec:eval}).
\end{itemize}

\paragraph{Research questions.}
\textbf{RQ1:} Can a static verifier detect the four defect classes in serverless
workflows before deployment? \textbf{RQ2:} Can the semantics \asl{} omits be
recovered cheaply enough to analyse existing workflows? \textbf{RQ3:} What is the
cost of verification and what runtime overhead does it impose? We answer these in
Section~\ref{sec:eval}.
