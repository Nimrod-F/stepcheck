\section{Approach}
\label{sec:approach}

\subsection{A two-layer analysis model}

\tool{} separates what can be checked from \asl{} alone from what needs recovered
semantics. \emph{Native} analyses (Layer~A) are sound and require no annotations:
structural well-formedness, and \asl{}-semantic data-binding checks such as a
\texttt{waitForTaskToken} task that never passes its task token, misuse of the
\texttt{\$\$.Map} context, and syntactically invalid JSONPath payloads.
\emph{Semantic} analyses (Layer~B) ---typestate, retry safety, compensation, and
typed contract compatibility--- consume an \emph{annotation} layer that records the
task semantics \asl{} omits. The annotation layer has two sources, in priority
order: explicit annotations (authored by hand or produced by the typed DSL
frontend), and \emph{inference} that supplies defaults from naming and resource
conventions. Findings derived from inferred facts are reported at \emph{warning}
severity, while findings derived from declared facts are \emph{errors}; this single
rule keeps confidence visible throughout the tool's output. We are deliberate about
what ``verification'' means at each layer: the native checks are \emph{sound} and need
no input, whereas the semantic checks are only as strong as the semantics they are
given---with declared annotations they are precise errors, and in the zero-annotation
default they degrade gracefully to best-effort, inference-driven \emph{warnings}
(typestate, having no labels to act on, simply stays silent). \tool{} is thus a sound
linter that becomes a precise verifier as annotations are added.

\subsection{Workflow model}
\label{sec:approach:model}

We model a workflow as a graph of states with a designated start. Beyond its
control-flow successors, a \emph{task} carries four pieces of semantic information.
\textbf{Contract:} a task $T:A\rightarrow B$ consumes/produces record types (field
sets); adjacent $T_1:A\rightarrow B$, $T_2:C\rightarrow D$ \emph{compose} only if $B$
provides every field $C$ requires (natively, without declared types, the layer instead
checks that JSONPath references resolve to data the workflow binds).
\textbf{Typestate:} $T$ advances a \emph{business state} $s_{\mathrm{in}}\rightarrow
s_{\mathrm{out}}$; a workflow is well-ordered when each task consumes the state its
predecessor produced, and an optional \emph{protocol} (e.g.\
\emph{created\,$\to$\,reserved\,$\to$\,paid\,$\to$\,shipped}) lists permitted
transitions. \textbf{Idempotency:} repeating an idempotent task causes no extra external
effect, so it may be retried freely; a non-idempotent one may not be retried on broad
error classes. \textbf{Persistence/compensation:} a \emph{persistent} task commits a
durable resource (reservation, charge, created record) that a later failure should undo,
so it needs a \emph{compensation}---an explicit handler or a \texttt{Catch} to a
compensating state. This vocabulary is deliberately lightweight---no separate formal
calculus---yet exactly what the four checks of Section~\ref{sec:analyses} consume.

\subsection{The annotation layer}
\label{sec:approach:annot}

Explicit semantics are supplied either through a \emph{sidecar} file attached to an
existing \asl{} workflow (Listing~\ref{lst:sidecar}) or, for greenfield workflows,
through a typed builder DSL that emits both the \asl{} and its annotations (one
\texttt{.task(\dots)} call per state carries its schema, protocol edge, idempotency,
persistence, and compensation). The two routes resolve to the same internal
representation, so the analyses are agnostic to how a workflow was authored.

\begin{lstlisting}[style=base,caption={A sidecar annotation (TOML), excerpt.},label={lst:sidecar}]
[schemas.OrderReserved]
fields = ["orderId", "amount", "reservationId"]
[tasks.ChargeCard]
idempotent = false
persistent = true
compensation = "RefundPayment"
state_in = "OrderReserved"
state_out = "OrderPaid"
\end{lstlisting}

\subsection{Inference of default annotations}
\label{sec:approach:infer}

Most existing workflows carry no annotations, yet their task names and resource ARNs
are highly conventional. \tool{} exploits this with a documented, configurable
heuristic that classifies each task from a lowercased \emph{signal} (its name, its
\texttt{Resource}, and parameters such as \texttt{FunctionName}). The heuristic uses
four small keyword sets: \emph{read} verbs (\texttt{get}, \texttt{list},
\texttt{describe}, \texttt{query}, \texttt{validate}, \dots) imply idempotent and
non-persistent; \emph{write} verbs (\texttt{create}, \texttt{charge}, \texttt{send},
\dots) imply non-idempotent; \emph{resource-acquiring} verbs (\texttt{reserve},
\texttt{pay}, \texttt{provision}, \texttt{putItem}, \dots) additionally imply
persistent; and \emph{notification} verbs/resources (\texttt{notify},
\texttt{publish}, \texttt{:sns:}, \dots) are non-idempotent but, being
fire-and-forget, never persistent. When no keyword matches, the heuristic
\emph{abstains}, leaving the task unclassified rather than guessing. Inference thus
yields a zero-effort default whose mistakes (Section~\ref{sec:eval}) are visible
(warnings) and correctable (an explicit annotation always wins).

\subsection{Architecture}

The pipeline is a straight line: a \emph{frontend} lowers a surface syntax to a
format-agnostic intermediate representation (IR); annotation resolution attaches
declared and inferred semantics to the IR; a \emph{pass} pipeline runs the five
analyses, each emitting coded diagnostics; and an \emph{emitter} lowers verified
workflows back to \asl{}. The design is modular along two axes: a new input format is a
new \texttt{Frontend}, and a new check is a new \texttt{Pass} (Section~\ref{sec:impl}).
